# Content Guide

Data file schemas and where each kind of content actually lives. See
[ARCHITECTURE.md](ARCHITECTURE.md) for how these files get *turned into* pages, and
[DEPLOYMENT.md](DEPLOYMENT.md) for how to verify a change after rebuilding.

**Rule of thumb:** if it's under `site/majors/`, `site/founders/`, `site/index.html`, or
`site/js/videos.js`, it's generated — don't edit it. Edit one of the sources below, then
run `python3 scripts/build_site.py`.

| To change | Edit | Then |
| --- | --- | --- |
| A use case's title, description, or difficulty | `site/data.json` (or re-run `extract_data.py` if the xlsx changed) | rebuild |
| Which video a use case links to, or its starter prompt | `site/data/videos-config.json` | rebuild |
| Upcoming campus-event data | Run `python scripts/sync_hws_content.py --events-only` | rebuild |
| Club-directory publication approval | `site/data/hws-content-config.json` and `docs/HWS_CONTENT_SOURCES.md` | sync clubs, then rebuild |
| Team roster, meeting time, site-wide copy, Skool member count | constants at the top of `scripts/build_site.py` | rebuild |
| Founder bios/roles/links | `FOUNDERS` constant in `scripts/build_site.py` | rebuild |
| Styling | `site/css/styles.css` | no rebuild needed |
| General interactive behavior (filters, copy button, deep links) | `site/js/site.js` | no rebuild needed |
| Campus-hub filtering and live refresh | `site/js/campus-hub.js` | no rebuild needed |

Never hand-edit `site/data/hws-events.json` or `site/data/hws-clubs.json`. They are validated
snapshots written by `scripts/sync_hws_content.py`. The clubs snapshot must remain empty
and the publication gate must remain false until written HWS approval is recorded.

## `site/data.json` (generated by `extract_data.py`)

```jsonc
{
  "majors": [
    {
      "number": 1,
      "slug": "africana-studies",          // slugify(name): lowercase, non-alnum → "-"
      "name": "Africana Studies",
      "programLink": "https://...",         // HWS program page, from the xlsx
      "useCases": [
        {
          "number": 1,
          "title": "…",
          "difficulty": "Easy",             // "Easy" | "Medium" | "Hard"
          "level": 1,                       // 1:Easy 2:Medium 3:Hard — must agree with difficulty
          "description": "…"
        }
        // ...exactly 20 per major
      ]
    }
    // ...exactly 42 majors, 840 use cases total
  ]
}
```

`site/js/data.js` is the identical object assigned to `window.HWS_AI_DATA` — a browser-
loadable copy, not a separate source. Both are written together by `extract_data.py`; never
hand-edit one without the other (in practice: never hand-edit either — re-run the script).

## `site/data/videos-config.json` (hand-maintained — the single source of truth for videos + prompts)

The file's own `_comment` field states this explicitly. Top-level keys, each read by
`build_site.py` at import time:

- **`skill`** — `{ archetype: { id, title } }`. Maps a task archetype to its default
  YouTube video. Every id here was verified live via YouTube oEmbed before being added —
  do the same for any new entry.
- **`leadVerb`** — `{ word: archetype }`. Fast path for `classify()`: if a use case title's
  first word is a key here, that's the archetype, no regex needed.
- **`rules`** — `[[archetype, regex], ...]`, checked in order against the lowercased
  title+description when `leadVerb` doesn't match. Order matters — first match wins.
- **`overrides`** — `{ "major-slug/use-case-number": video_id }`. Hand-routes one specific
  use case to a video other than what `classify()` + `skill` would pick. If the target video
  isn't already a value somewhere in `skill`, add its id to `_EXTRA_ARCH` in
  `build_site.py` too (see [ARCHITECTURE.md](ARCHITECTURE.md#use-case-card-logic-the-part-that-spans-files)) —
  otherwise its prompt archetype silently falls back to `general`.
- **`videoMeta`** — `{ video_id: { title, channel, ... } }`. Feeds `VideoObject` JSON-LD and
  the "linked tutorial" attribution.
- **`videoTeaches`** — `{ video_id: { method, takeaway } }`. Feeds `card_text()` — what the
  card says the tutorial covers, and the post-task takeaway line.
- **`promptPatterns`** — `{ archetype: instruction_text }`. The task-specific tail appended
  to every starter prompt of that archetype. Must include a `"general"` entry as the
  fallback for any archetype without its own pattern.

**Every tutorial video was watched end-to-end before being linked**, and card copy names
its real title, channel, and year — don't add a video id without adding matching
`videoMeta`/`videoTeaches` entries, and don't repurpose an existing video's id for an
unrelated archetype.

## Team, founders, and organizational constants (`scripts/build_site.py`, top of file)

Not JSON — plain Python data, because they're small, rarely change, and benefit from being
next to the code that renders them:

- `TEAM` — list of `(initials, name, role, blurb, avatar_class)` tuples, rendered by
  `team_cards()`.
- `FOUNDERS` — list of dicts (slug, name, role, bio, links, `school`, `memberOf`, photo
  info, etc.), each rendered as its own page by `build_founder()`. Sourced from
  [`research/founders/`](../research/founders/README.md) — that directory's per-subject
  `README.md` has the distilled profile and proposed bio copy; `web-research.md` and
  `sources.md` carry the provenance tagging (`[verified]`/`[supplied]`/`[unconfirmed]`).
  Resolve any `[unconfirmed]` claim with the founder before it goes on the public page.
- `LICOM`, `SUNDAI`, `ORG_URLS` — organizations referenced in founder link rows and
  `worksFor`/`memberOf` JSON-LD.
- `SKOOL_URL`, `SKOOL_MEMBERS` — the club's community hub link and member count shown as
  social proof on the homepage. `SKOOL_MEMBERS` is a hand-updated number, not fetched live —
  update it when it drifts noticeably from reality.
- `MEETING`, `MEETING_START/END/TZ`, `COLLEGE`, `LOCATION`, `BASE_URL` — site-wide copy and
  the `Event`/`EducationalOrganization` JSON-LD on the homepage. `BASE_URL` is the one place
  to change if the site ever moves to a custom domain.
